# Design decision log

Settled questions, so each session does not reopen them. Entries are append-only. Change a decision by adding a new entry that supersedes the old one.

Status: `open` while unanswered, `proposed` until the council or the maker confirms it, `locked` once confirmed, `codified` once tests or tokens enforce it, `superseded` once replaced. Nothing here is `locked` as of 2026-10-31. Confirmation of product-wide choices belongs to the council. See [open decisions](../../docs/platform/open-decisions.md).

## DL-001: DESIGN.md is the single source of tokens

**Status:** codified. Root `DESIGN.md` in the DesignMD format holds all tokens and reasoning. `packages/design-system/scripts/generate-tokens.mjs` produces CSS and JSON, and tests fail on stale output. Green Goods and Coop use the same format. Groups the format lacks (fonts, motion, shadows) live in a fenced block in the same file, so there is still one source. The linter runs on a pinned `@google/design.md` 0.4.0, a newer release than Green Goods' 0.1.1.

## DL-002: Keep every website value

**Status:** codified. The website's dark values are ramp step 400 and its light values are step 700. New steps extend the ramps. A pinned copy of the website's tokens and a test prove nothing drifted. `--pad`, `--card-radius`, the RGB triplets, glow and grain are all preserved under their website names.

## DL-003: Public ink-dim becomes the token

**Status:** codified. The website's token file has `--ink-dim` at `#787060` and `#8A7A60`, which fail text contrast, and its public pages override them with `#A49A87` and `#5D503B`. The overrides become the token, which also fixes the steward desk. The originals retire. `soil-600` (`#86765D`) serves as the control boundary in both themes, slightly darker than the light original so it holds 3:1 on tinted panels.

## DL-004: Follow the system theme, with explicit generated blocks

**Status:** codified. The default follows the operating system. `data-theme` pins a page or a section, and the website pins dark. Tokens use media and attribute blocks instead of `light-dark()`, because the website's RGB triplets and non-colour theme values cannot use it and these blocks work on older phones that `light-dark()` would leave unstyled. Generation removes the cost of repeating values. In the app the control lives in settings, not the header.

## DL-005: Eight capitals get eight colours within the palette

**Status:** proposed. The website uses six tokens in about three hue families, so Intellectual matches Living and Cultural matches Spiritual. This system moves Intellectual to circuit and Spiritual to signal, adding no new hue. Several pairs still look alike under colour blindness, so colour only groups, and the word and glyph identify. Links do not use signal. The website's map keeps its colours until it adopts this.

## DL-006: Capital glyphs are square tiles

**Status:** proposed. The website uses small circles. A square tile with a 2 px radius reads like a specimen label, holds two letters at the 14 px label size, and fits the small-corner language. Tiles have three states: filled, dashed and hollow.

## DL-007: Pencil and ink

**Status:** codified in the patterns. Dashed means an assistant suggested this and no person has confirmed it. Solid means confirmed. This applies to proposals, tiles and imported records. It carries the product rule that nothing derived is applied silently, using the field notebook metaphor.

## DL-008: Corners are 2, 4 and 8 px

**Status:** codified. 2 px for cards, tags and tiles, matching the website's `--card-radius`. 4 px for buttons and inputs. 8 px for sheets and dialogs. Full only for avatars and dots. *Refactoring UI* notes suggested 4 px for cards, but we kept the website's value. No pill buttons. Organic blob outlines stay on website marketing pages.

## DL-009: Add Latin Extended font subsets

**Status:** open. The self-hosted fonts are Latin only. Portuguese and Spanish are covered. Yoruba's dotted vowels and Vietnamese fall back to the system face. Add `latin-ext` subsets before launch in places that need them, and measure the added weight.

## DL-010: 12 px floor, sentence case, two weights

**Status:** codified. 12 px is the smallest text. Buttons and labels use sentence case. Task screens use weights 400 and 600. Weight 300 starts at 48 px. The website's 0.52 to 0.65 rem tracked capitals retire when it adopts the scale. Capitals survive in one small label, used only to say what kind of record something is.

## DL-011: Add madder for errors and destruction

**Status:** proposed. The website has no error hue, and uses copper plus thicker borders. Destructive confirmations and form errors need something distinct from the copper accent, so this system adds one red ramp named after a plant dye. It is always paired with an icon and words.

## DL-012: Class prefix, data attributes and cascade layers

**Status:** codified. Classes start with `rc-` to coexist with the website's global classes during migration. Variants use data attributes and ARIA state. Cascade layers follow the atomic levels, so larger patterns can specialize smaller ones without specificity tricks. No BEM and no utility framework. CSS nesting is avoided so older phones keep working.

## DL-013: The system lives here until a second consumer needs it

**Status:** proposed. `packages/design-system/` is self-contained, outside `dist/`, so deploys are unaffected and it can move to a shared `regen-commons` repository when the website or desk adopts it. Moving it is an [open decision](../../docs/platform/open-decisions.md).

## DL-014: Plain labels first, tested with people

**Status:** proposed. Domain terms stay in data and documents. People read plain labels, listed in [VOICE.md](brand/VOICE.md#plain-names). Each one is a hypothesis for [usability testing](principles/usability-testing.md). "Initiative" stays as the default because it is the community's word, with "project or group" as the test alternative.

## DL-015: One CSS source, thin React components

**Status:** proposed. React components in `packages/app/src/ui` render these classes and own no visual CSS. The *Atomic Design* notes proposed CSS modules per component. One global layered source keeps the library, app and website adoption simple. Revisit if class collisions appear.

## DL-016: Static pattern library for now

**Status:** proposed. Plain HTML pages show the patterns until React exists. They load the same CSS and need only a static server. Storybook stays deferred, and a live `/library` route replaces these pages in Phase 0.

## DL-017: Fit is a word, not a number

**Status:** proposed. Match strength shows as Strong, Good or Possible fit plus bar length. The PRD's scores stay internal. *Refactoring UI* treats a score as data worth showing, such as a percent. Here, people have not seen the rubric, and scores built from sparse data would imply more certainty than exists, so plain words win.

## DL-018: The save prompt is inline, once per seam

**Status:** proposed. Saving appears as a panel in the page flow, after a person has seen value, never as a modal or wall. The panel is the same pattern everywhere. A dismissed prompt stays dismissed. See [08-accounts-and-saving.md](../../docs/platform/08-accounts-and-saving.md).

## DL-035: Records open as sheets over their list

**Status:** maker's call, 10 November 2026, from the maker's second design review; the council items it touches stay open. Dialog gains a third presentation, detail, beside information and task. ## DL-114: Several drafts live in a new database, and an older tab is left as it is

**Status:** user decision, 19 November 2026 ("New database + reload", and "Yes, delete both" for removals). The reload was then built, reviewed and dropped the same day ("Drop the reload"); its record is at the end of this entry. Amends the storage of DL-112 before it was released.

DL-112 first upgraded the released build's database to keep several drafts. A second review found what that costs. A tab still running the released build closes its connection when the database is upgraded, and every later attempt to open it at the old version fails, so words typed there are never stored. A rollback to the released build fails the same way on every browser that ran the new one. Nothing is deleted in either case, but no draft opens.

Several drafts now live in a database of their own. The released build's database is left at its version and is never upgraded: this build opens it without asking for a version, reads it and closes it. So an older tab keeps storing with no error, and a rollback finds its draft as that build last wrote it. The first run copies that draft and its backups across and deletes nothing. A person who never used the released build ends with no such database at all.

An older tab cannot tell this build that it wrote, so this build looks again: at every start, when a tab comes back on screen and when Your Initiatives opens. Words typed in an older tab after the copy become the draft here. When both builds changed it, the later edit wins by the time each stamped on it, and the other version is kept as a device backup that Settings can restore, as two tabs already do. That backup is kept under a key of its own and no cap ever drops it. An older tab never takes this build's edits, so round after round each one may hold words kept nowhere else, and the cap of three that two tabs of this build share would have deleted the first at the fourth round. They add up while an older tab stays in use, and only the person deletes them. A draft removed here stays removed, and comes back only if the older tab writes to it again, because that tab still shows it.

The copy never changes the released build's database. A removal the person asks for does: deleting a device backup for good also deletes its copy there, and the draft itself goes once nothing of that initiative is kept here. Otherwise "removed from this device" would be untrue for what was copied, and a rollback would bring back something a person deleted. The deletion looks at the older storage first. Words an older tab typed since the last look come across, and that tab's draft is left as it is so the tab goes on storing. The page says what it found, in words true for each case: the words are in Your Initiatives again; or, where this build's own edit was the later one, they are kept as a device backup; or they could not be read just now and are still where the older tab stored them. When the older storage cannot be checked at all, nothing is removed and the page says so. When it does not confirm its own removal, the page says only that this backup is still here, because whether the older copy went is not known. The draft there is removed only at the version this build has seen, and only when this build may hold nothing more of the initiative: no draft or backup with its ID, none standing for the same saved card under another ID, and none it cannot read. An older tab still open on a draft that is removed this way stops storing at its next keystroke and says so, with its words on its page: that build treats a missing draft as a conflict. A removal that can be undone, which keeps a backup, changes nothing there.

What a rollback hides until this build returns: every initiative started in it, every edit made in it to the copied draft, and the backups made in it. They stay in the new database, untouched.

**What an older tab does after a release.** Nothing reloads it. It keeps the app it loaded until the person reloads or reopens it, it keeps storing to that build's own database with no error, and this build picks its words up at its next look. The one thing a person might notice is two tabs showing different screens, one from each build. That is the normal state for a while after any release, and not only for a tab left open: measured on production on 19 November, a returning browser was served the earlier build from the service worker's cache through two page loads, and showed the new build on the load after the worker had updated.

**The reload that was dropped, and why.** This entry first had the service worker reload tabs that were not on screen, two seconds after a new version took over, so that older tabs would not linger. It was built and then removed before release, and should not be added back without this record.

- It could discard words. The released build stores its main box on every keystroke, but it keeps the words typed into the add-by-hand box on needs and offers on the page until they are added, and a tab whose storage has failed holds its words nowhere else and tells the person to keep it open. Typing a need and then opening Weave in a second tab hides the first tab and triggers the update, and two seconds later the first tab was reloaded and those words were gone. That is an ordinary thing to do.
- A worker cannot tell. It sees whether a tab is hidden, not what its page holds, and the released build cannot be asked.
- It was not needed. With a database of its own, this build leaves an older tab working, so the reload only shortened how long such a tab lives.
- It had two faults of its own, found on the way. Holding the worker's start-up open for the reloads deadlocked, because a reload is a page load the worker cannot answer until it has started, and every page of the site hung in a real browser. And it reloaded a tab at the address the worker knew for it, which after a move inside the app is not always the page on screen.

A reload that cannot lose words has to ask the page: the worker posts a message, and only a tab that answers that it holds nothing unstored reloads itself, at its own address. No answer means no reload. The released build would never answer, so that design does nothing for this release and could only begin to work between two later versions. It would be a change of its own.

Something deleted in an older tab after the copy stays in this build until it is deleted here.

The first read gives the older storage three seconds and then goes on without it, so a hang there never leaves typed words unstored. What it holds is shown when it answers. Every other wait on it is bounded too, at eight seconds: a look that gets no answer gives up quietly and is tried again at the next look, and a deletion takes about ten seconds at most: eight for the check and the removal together, and up to two more to read words an older tab typed in between. Then it says what it did not do and lets its dialog close. A version that holds the same content as this build's and differs only in bookkeeping (when and how often it was written, and the note of how the last fill ran) makes no backup. Content includes the card binding, saved, pending and retired, and the record of what the assistant did, so a version that differs only in which card it is saved as is never dropped. When the words are the same and only the binding or the assistant record differ, this build's version stays as the draft, whichever was written later, and the older tab's is kept as a backup: that tab never saw this build's save, and its version would show a saved card as "Not saved yet", or save the same words again as a new card after a deletion. The two builds store their keys in different orders, so the comparison does not depend on order. A deletion has one bound for its check and its removal in the older storage. When the bound is reached the removal there is called off, so a late commit cannot contradict the message, which says only what is certain: this backup is still here, and its copy there may or may not have been removed. When the copy there was removed and this backup then could not be, the message says exactly that. What a deletion brought across before it stopped is shown all the same, and a tab of this build that writes over words it brought across keeps them as a between-builds backup, outside the cap.

## DL-119: A card's Certified project is chosen once and kept on the device

"New", "Lake", "Gulf of" and their like stay joined to the place they name ("New Mexico", "Gulf of Mexico"), and a country's name is matched whole, so "islands" is no country. Kept on purpose: "I work in" still names a place, since it is how a founder working alone says where, though it also reads "I work in Dubai and send money home" as Dubai.

**Amended 24 November 2026: About it is the initiative's own description** (user decision in the extraction brief: About it holds the initiative's own description, in the person's own words, without the speaker's name or what the initiative needs or could offer). Nothing is reworded: whole sentences and clauses are left out, and only the first letter of what is left is made a capital when its sentence's start went. What the work aims at or gives stays, because it describes the initiative ("We need to restore the river", "We offer free repair workshops", "Buscamos fortalecer la soberanía alimentaria"). If nothing would be left, the words stay as they are, so About it is never emptied, and a pointer to the card's link ("Visit … for our opening hours") is left out only when its last word names something to read there and something else is left ("Visit … for free repair workshops" stays). A name said without capitals and without "my name is" stays, since the word could be part of the description. Where keywords cannot tell an ask from what the work does, the words stay: a clause that asks and has a second subject ("We need a van and the kitchen feeds 200 families"), "need to find homes for rescued dogs", "We can host up to 40 children", "The school needs a garden, so we built one".
